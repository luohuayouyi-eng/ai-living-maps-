认识方法

01 / METHOD · 系统观 × 发展观

AI 辅助设计不是一个孤立的工具问题。系统观帮助我看见数据、模型、界面与工作流之间的关系；发展观帮助我理解这些关系如何随时间演化。

LENS / 01 · SYSTEM VIEW 系统观

局部最优，不等于整体更好

在 AI 辅助设计中，数据、模型、交互界面和用户工作流彼此定义。把其中一环做到极致，未必能让整个设计过程变好。

DATA 数据 规范 · 组件 · 场景
›
MODEL 模型 生成 · 评估 · 迭代
›
INTERFACE 交互界面 提示 · 选择 · 编辑
›
WORKFLOW 工作流 调研 · 评审 · 交付

↺ 模型输出改变界面上的选择，界面又改变团队的工作流；工作流产生的新数据再回到下一轮生成。

  • 数据 → 模型

    数据决定模型能学到什么。规范、组件和真实场景不足时，模型常用“平均风格”补齐，生成结果看似完整，却可能不适合具体业务。

  • 模型 → 界面

    模型越能一次给出大量候选，界面就越需要解决筛选、比较、编辑和信任问题。否则，生成得越快，设计师的决策负担越重。

  • 界面 → 工作流

    如果界面把“一键生成”设成默认路径，团队可能跳过用户研究和设计评审；节省下来的操作时间，会转化为后期的返工与协调成本。

因此，只优化模型分数或生成速度，并不能保证整体体验改善。真正的设计对象，是数据、模型、界面与工作流共同构成的系统。

LENS / 02 · DEVELOPMENT VIEW 发展观

从替代操作，到协同判断

AI 设计工具经历了从局部自动化到生成式辅助，再到协同创作的演进。每一次能力扩展，都会同时解决旧问题、暴露新边界。

01

单一功能自动化

自动对齐、批量替换、图标补全。解决重复操作耗时，但人仍是操作主体，工具并不理解设计任务。

02

生成式局部辅助

文生 UI、风格探索、代码草稿。解决从 0 到 1 的候选不足，但结果波动大，评审与筛选成本随之上升。

03

人机协同创作

约束生成、多候选、局部锁定、多轮修订。设计师从执行转向定义与判断，但新的责任边界也随之出现。

NEW BOUNDARIES / 新限制
版权与原创性 可控与可复现 责任归属 能力迁移

训练来源与生成过程不透明，成果不能默认可商用；随机性带来探索空间，也让规范统一和版本复现更难；当错误发生时，模型、工具设计者与使用者之间的责任需要被重新分配。

发展观提醒我：工具升级不是零成本的替代，而是把问题迁移到新的层级。判断一种新方法时，要同时问它解决了什么、又隐藏了什么。

分析案例

02 / CASES · 从问题到判断

两个案例使用不同方法，但都沿着同一条判断链展开：具体问题 → 使用的方法 → 依据与比较 → 当前判断。它们分别对应工具设计与边界检查两类问题。

01
CASE 01 / TOOL DESIGN 设计情境

生成速度、规范遵循与用户控制，如何同时成立？

情境：为设计团队构思一款 AI 辅助 UI 生成工具。工具接收需求描述与设计规范，输出可继续编辑的界面草案。

问题定义 多目标取舍
01

具体问题

QUESTION

只追求一键生成，输出可能偏离组件库和业务约束，设计师也难以判断应该改哪里；若提供过多参数，启动成本又会上升。速度、规范遵循和控制感之间存在直接冲突。

02

使用的方法

METHOD

用「问题定义」把目标从“生成更快”改写为“更快形成可持续修改的高质量草案”；再用「多目标取舍」比较一键生成、约束生成与建议式协同三种路径，明确哪些目标不能被牺牲。

03

依据与比较

EVIDENCE & COMPARISON

比较维度不是单次生成耗时，而是首版时间、返工成本、规范通过率和主观控制感的综合。

三种 AI 辅助 UI 生成策略的比较
方案 收益 代价
一键生成 首版最快，适合发散阶段。 规范遵循不稳定，修改路径不清晰，控制感最低。
约束生成 可导入组件库与设计规范，规范通过率更高。 前期配置成本较高，灵活性受到约束。
建议式协同 提供候选、理由、局部锁定与回滚，控制感最强。 交互复杂度最高，要求设计师具备更强的判断能力。
04

当前判断

CURRENT JUDGMENT

我倾向于采用「约束生成 + 建议式协同」的混合方案：默认在规范约束下生成候选，关键区域允许锁定、替换和回滚，同时保留生成理由与版本记录。生成速度应作为约束条件，而不是唯一优化目标。下一步可用原型对比三组的首版时间、返工次数与设计师主观控制感。

02
CASE 02 / BOUNDARY CHECK 公开案例

当生成结果“像”已有作品，失败发生在哪一层？

2024 年 7 月，Figma 的 Make Design 功能被用户指出部分生成结果与 Apple Weather 高度相似；Figma 随后暂时关闭该功能并展开审查。

系统拆解 边界检查
01

具体问题

QUESTION

生成式 UI 工具把结果直接呈现为“可用”的设计草案，但相似性、来源和原创性边界没有被清楚标出。当生成结果与已有作品高度相似时，团队可能在缺少审查的情况下把它带入交付。

02

使用的方法

METHOD

用「系统拆解」把工具拆成数据/参考、模型生成、交互选择、团队工作流四层；再用「边界检查」逐层追问：它能保证什么、不能保证什么，哪些风险必须由流程补上。

03

依据与比较

EVIDENCE & COMPARISON

公开报道显示，这一争议不能简单归因于“模型抄了某个作品”。更有解释力的视角是：熟悉的视觉模式在数据与生成过程中被强化，而界面缺少相似性提示，工作流又没有独立的原创性审查。

数据 / 参考 高相关

相似的参考分布与既有界面，使生成结果更容易靠近熟悉样式。

模型 中相关

倾向复用高频视觉模式，但不能单凭生成行为判断为直接复制。

交互 中相关

结果以成品草案出现，缺少相似度与来源提示，用户难以判断边界。

工作流 高相关

没有原创性和法务审查，相似结果可能直接进入交付。

与人工参考相比，人工设计同样会借鉴，但通常可以说明参考来源与改编过程；生成系统默认不暴露这种过程。因此，问题不在“是否看了参考”，而在边界是否可见、是否有人负责。

依据来源： The Verge — Figma pulls AI tool after criticism that it ripped off Apple’s design（2024-07-02）

04

当前判断

CURRENT JUDGMENT

这更像是数据/参考、交互提示与工作流的联合失败，而不是单纯的模型能力问题。使用 AI 生成 UI 时，应把输出定义为概念草案：增加来源记录、相似性提示和人工原创性审核，并把“是否可商用”移出工具承诺，交给明确的组织流程。

成长习惯

03 / HABITS · 团队实践

把方法变成习惯，才能让 AI 真正参与设计，而不是替代判断。以下三条是我们希望在项目中持续保持的实践。

HABIT / 01

先问用户问题，再选 AI 工具

先确认用户、场景与成功标准，再判断该用生成、检索还是人工分析。工具选择跟随问题，而不是反过来。

PROBLEM FIRST
HABIT / 02

保留输入与输出记录

记录提示词、模型版本、参考素材、候选结果和选择理由，让协作过程可复盘、可解释、可追溯。

TRACEABLE
HABIT / 03

主动寻找反例与边界

持续收集不可落地、偏见、版权争议等反例，检查模型、数据、交互与工作流的边界，并把结论写回流程。
